# Architecture

The active implementation is `platforms/ios/`: SwiftUI with UIKit/TextKit
bridges, generated by XcodeGen. There is one app target and one hosted test
target. Other clients and a shared cross-platform core are deferred.

## Runtime and storage

`ListsApp` creates one `ItemStore` rooted at app-private `Documents/Lists/`.
`ContentView` hosts loading/recovery state and the shared `CalendarPreferences`;
`SidebarView` owns navigation, search and the persistent `ItemMoveSession`.

Screens mutate the store. `ItemStore` publishes optimistic state, serializes
disk writes and retains failed field intents for retry. Its maintenance gate
waits for existing writes before rebuild/export/replacement and queues later
mutations in arrival order. Preserve these rules when simplifying callers:

- Newer edits must survive suspended or failed older writes.
- Item parent, list and section relationships stay coherent. Moving or deleting
  a parent cascades to descendants; list-parent cycles and inactive destinations
  are rejected or repaired during load.
- Multi-file delete/restore uses durable recovery records and ordered commits.
  An incomplete recovery pauses unsafe repair, expiry and permanent deletion.
- Failed or ambiguous files are retained/quarantined and reported, rather than
  silently discarded. `lamport` participates in duplicate list-header selection.

`FileStore` owns paths and file I/O. A list directory contains `.list.yml`,
title-based Markdown item filenames and optional child-list directories.
Stable ids remain in frontmatter. `FrontmatterCodec` uses Yams and preserves
unknown item metadata, including unsupported custom-property values.

`AttachmentStore` confines paths to the library, imports original bytes and
quarantines recoverable orphan files. Document attachments live under
`Attachments/`. Collection files live in a list's `.files/` directory, with
identity/order metadata and recoverable deletion records. Export snapshots the
library through the same maintenance gate.

## UI boundaries

List detail uses a UIKit collection-view bridge. Its sibling files separate
snapshots, rows, registrations, queries, reorder/drop policy and inline editing.
`ListDetailColumnsLayout` lays out real named sections as Kanban columns.
`ListHierarchyRevealSession`/`Host` and `SubListBrowserView` reveal the same
hierarchy rows used by Home above the navigation container.

Move mode belongs to `ItemMoveSession`, with a persistent shelf across navigation.
Only user-list destination rows commit placement through the store. Ordinary
dragging remains local reorder/nesting. `ItemHierarchy` and `ListHierarchy`
provide pure shared answers without file-write access.

`ItemDocumentView` is the document route; `ItemDetailSheet` is its thin router.
`DocumentPageRows` and `DocumentEditorBridges` host the title, tags and body.
`DocumentMetadataCard.swift` contains the on-page property rail and advanced
built-in property controls. The title has no keyboard accessory. Shared typed
field/value and saved-view editors live in `Features/Database`.
Quick Capture uses the same item model with a testable `QuickCaptureDraft`.

`CalendarPlannerView` is the shared calendar shell for user lists and applicable
queries. `CalendarProjection` produces scoped entries and virtual occurrences;
it never materializes documents just because a date is visible. Timeline
geometry/gesture helpers separate continuous previews from committed dates.
Calendar mutations use `ItemStore`, and display state stays in preferences.

`CalendarConnections` reads EventKit after explicit permission and persists
device-local source mappings/import ledgers. `CalendarImport` owns merge and
conflict rules; per-item source baselines are portable frontmatter. Neither
writes to EventKit. `SearchDictation` provides explicit on-device voice input.

## Database projections

`DatabaseField` and `DatabaseView` are portable list metadata. Optional field
identity/type/option descriptors extend the existing ItemCustomProperty rather
than replacing Markdown storage. `DatabaseSchema` validates typed values,
resolves unambiguous legacy text fields and preserves opaque future type names.
`DatabaseQuery` filters/sorts items and retains ancestor context without writes.
`ItemStore+Database` binds legacy identities before definition renames; ordinary
store mutations, ordered writes and retry semantics remain authoritative.

`DatabaseItemsView` renders Table and saved List/Columns projections. Named
Calendar views reuse CalendarPlannerView. Ordinary List/Columns stays on its
existing collection bridge. Destination mode falls back to existing move targets.
The selected named view is local preference; definitions and view configuration
travel in `.list.yml`. No remote database or duplicate item store is introduced.

CalendarConnections has an injectable event-source boundary. The production
adapter only reads EventKit; tests drive the same refresh/ledger/merge loop with
source fixtures. Errors are isolated by connection. Month Compact/Details reuse
the existing vertical pager and calendar projection alongside Month List.

## Markdown

`MarkdownStyler`, `MarkdownLayoutDelegate` and `MarkdownLayoutManager` preserve
source while styling and drawing Live Markdown. `EditorCoordinator` owns native
editing/selection and synchronizes external bindings after stale SwiftUI renders
have cleared. `MarkdownTable` supplies interactive table editing. Raw mode keeps
source directly editable.

`MarkdownCodeHighlighting` uses bundled Highlight.js through JavaScriptCore.
`MarkdownSyntaxRenderer` uses local-only WebKit and bundled KaTeX/Mermaid.
`MarkdownMedia` owns attachment boundaries, previews and local presentation
preferences. `MarkdownAudioRecording` retains an interrupted recording manifest
in Application Support until save/discard. No renderer fetches remote metadata.

`DocumentMarkdownIndex` resolves paths/headings, outlines and backlinks using
GFM parsing; store operations repair app-managed inbound paths during renames
and moves. `MarkdownBodyView` provides read-only rendering through MarkdownUI
and the semantic renderer.

## Dependencies and verification

Yams encodes storage; MarkdownUI renders read-only Markdown; CMark provides
direct GFM parsing; SnapshotTesting is test-only. Vendored renderer bundles,
registries, fonts, regeneration source and licenses are retained together.

Change project structure through `project.yml`, then regenerate with XcodeGen.
Storage changes need focused integrity coverage. UI/gesture changes need
appropriate hosted snapshots or verified simulator/device evidence. See
`AGENTS.md` and the snapshot guide for the local workflow.
