# Concurrency, Threading & Swift 6 Data Races Audit

## Verdict
**Minor issues — leaning Solid.** The threading architecture is genuinely well-chosen: a `@MainActor` store fronts a single `FileStore` *actor* that owns all disk I/O, file writes are atomic, and the project compiles in the Swift 6 language mode (strict concurrency *enforced as errors*, not just warnings). So classic cross-thread memory races on shared state are structurally prevented, and file I/O is correctly off the main thread. The remaining risks are **logical** races the compiler cannot catch: actor-reentrancy "lost updates" during the `await` inside every save, a couple of fire-and-forget `Task {}` writes whose ordering isn't guaranteed, and bulk loops that persist stale snapshots. None are guaranteed corruption on the common single-action path, but the lost-update class is real and worth tightening before sync ships.

## A note on the "warnings-as-errors is OFF" risk
`SWIFT_TREAT_WARNINGS_AS_ERRORS: NO` (project.yml:14) only governs *warnings*. With `SWIFT_VERSION = 6.2` and no language-mode downgrade or `SWIFT_STRICT_CONCURRENCY` override (project.yml:11, pbxproj:971/1047), the build runs the **Swift 6 language mode**, where data-race-safety violations are emitted as **errors** regardless of the warnings flag. So the concurrency safety the compiler proves here is real and cannot be silently ignored. The caveat in my brief — "warnings may be silently ignored" — does **not** apply to hard concurrency-isolation violations in this configuration; it would only matter if someone later flips the language mode back to 5 or sets strict-concurrency to `minimal`/`targeted`. **Recommendation:** keep the project in Swift 6 mode; that single setting is doing most of the heavy lifting here.

## Findings

### [P1] Actor-reentrancy "lost update" across the `await` in every `ItemStore` mutator
- **Where:** `Core/Stores/ItemStore.swift` — the read-modify-write shape repeats in `toggleDone` (77-91), `incrementHabit` (95-107), `setHabitCount` (110-124), `update` (185-195), `softDelete` (267-276), `restore` (279-288) and others.
- **What:** Every mutator does: (1) read `items.first(where:)` into a local `var`, (2) mutate the copy, (3) `try await store.writeItem(copy)`, (4) `items[idx] = copy`. `ItemStore` is `@MainActor`, so these are serialized — *except* at the `await`, which suspends and releases the main actor. A second mutator queued for the **same item** can run during that suspension, read the *pre-mutation* snapshot, and on resume both writers do `items[idx] = copy`, so the second-to-finish silently clobbers the first. The on-disk file ends up matching whichever `writeItem` ran last.
- **Impact:** Rapidly acting on one item — e.g. toggle-done immediately followed by flag, or toggle + a swipe outdent — can drop one of the two changes (a flag that doesn't stick, a re-checked box). The state is internally consistent (no crash, no corruption), it's just a *lost edit*. Low frequency today because the UI usually drives one action at a time and each `await` is brief; the probability rises with fast input and will rise sharply once background sync writes concurrently.
- **Confidence:** High that the interleaving is possible; Med that a user hits it on the current single-device build.
- **Fix:** Re-fetch inside the method after the suspension, or fold the disk write to the *end* and apply the in-memory mutation last (write-then-assign is already the order; the gap is that step 1's read is stale on resume). Cleanest: have mutators apply the in-memory change *first* (synchronously, before any await), then persist — so the last in-memory writer is also the last on disk. Or serialize mutations through a single per-item async queue. This matters most before multi-writer sync lands.

### [P1] Bulk loops persist a stale snapshot captured before their awaits
- **Where:** `Core/Stores/ItemStore.swift` — `renameTag` (232-256), `removeTag` (216-227), `migrateLegacySectionsIfNeeded` (538-570), `promoteOthersToSection` (396-414), `commitSectionEdits` / `deleteSection` cascade loops (476-530).
- **What:** These snapshot a set of items up front (`let affected = items.filter {…}`), then loop `try await update(copy)` over the *captured* copies. Each iteration's `await` releases the main actor. If the user (or another task) edits one of those items mid-loop, a later iteration's `update(copy)` writes the **stale captured copy**, discarding the interleaved edit. `renameTag`/`removeTag` rebuild only the `tags` array from the snapshot but write the *entire* item, so a body or due-date edit made during the loop is lost.
- **Impact:** Rename-a-tag or the one-shot legacy-section migration, run while the same item is being edited, can revert that item to its pre-edit state. The migration loop runs at bootstrap so it's mostly safe (no concurrent user input yet), but `renameTag`/`removeTag` are user-triggered from the Tags screen and are the realistic trigger.
- **Confidence:** Med. The window is the per-item write latency; a deliberate "rename tag while editing an item with that tag" could reproduce it, ordinary use rarely will.
- **Fix:** Inside the loop, re-fetch the current item by id and apply the field change to the *fresh* value (e.g. `guard var cur = items.first{ $0.id == id } else { continue }; cur.tags = …`) rather than writing the snapshot captured before the awaits.

### [P2] Two independent fire-and-forget `Task {}` writes per drag commit; ordering not guaranteed
- **Where:** `Core/Stores/ItemStore.swift` `applyUpdateSync` (200-212) and `applyReorderItemsSync` (162-183), both invoked back-to-back from `ListDetailCollectionView.performItemReorder` (1587-1596).
- **What:** A drag that both reparents and reorders calls `applyUpdateSync(copy)` then `applyReorderItemsSync(...)`. Each spawns its **own** unstructured `Task {}` to persist. There is no ordering guarantee *between* the two Tasks. In practice the in-memory mutation in both methods is applied **synchronously** before the Task is spawned, and each Task re-snapshots the (already-updated) `items`, so both disk writes carry the parent/section change and `FileStore` (an actor) serializes them — on-disk state converges correctly either way. The hazard is fragility, not current corruption: the pattern relies on the synchronous in-memory mutation always preceding the async write, and on no third mutator interleaving between the two Tasks.
- **Impact:** None observed on the happy path. The smell is that "apply two related disk mutations as two detached tasks" is exactly the shape that *becomes* a corruption bug under a future refactor (e.g. if someone makes the in-memory apply async, or adds a write that doesn't re-snapshot).
- **Confidence:** Med (that it's currently benign); High (that it's a maintainability/ordering hazard).
- **Fix:** Coalesce into one `Task {}` that performs both writes in sequence, or give `ItemStore` a single serial persistence task/queue that all mutations funnel through. Also note `applyReorderItemsSync` swallows write errors with `try?` (180) — a failed reorder write leaves disk out of sync with the in-memory order silently.

### [P2] `bootstrap()` has no re-entrancy guard against a double `.task` fire
- **Where:** `Core/Stores/ItemStore.swift` `bootstrap` (23-49); invoked from `App/ListsApp.swift:13` via `.task {}`.
- **What:** `bootstrap` calls `loadAll`, and if the result is empty, seeds sample lists/items. `isLoaded` is set only at the very end. If `.task` were to fire twice for the same store before the first completes (view-identity churn, or a future second call site), two concurrent bootstraps could both observe an empty disk and both seed `makeInbox()` + sample data, producing duplicate Inbox/sample lists. `FileStore` serializes the writes but doesn't dedupe the logical work.
- **Impact:** Duplicate seeded lists on first launch. Unlikely on the current single `WindowGroup` with a stable `@State` store, but there's no guard if a second entry point is added.
- **Confidence:** Low — I could not construct a current path that double-fires `.task` for this `store`; flagging the missing guard, not a reproduced bug.
- **Fix:** Early-return if `isLoaded` (or an `isBootstrapping` flag) is already set, or make bootstrap idempotent by keying the seed on "Inbox already exists."

### [P3] `schedule` does a sync `cancel` then `await center.add`; concurrent schedules race on content
- **Where:** `Core/Notifications/NotificationScheduler.swift` `schedule` (47-75).
- **What:** `schedule` calls `cancel(item.id)` then `await center.add(request)`. Two near-simultaneous `schedule` calls for the same item (e.g. two quick `update`s) can interleave their cancel/add. Because `UNUserNotificationCenter` keys pending requests by identifier (the item UUID), the net result is still exactly one pending request — last add wins on content. No duplicate or orphaned notification.
- **Impact:** Effectively none; worst case the notification reflects the second-to-last edit for a sub-second window. Mentioned only for completeness.
- **Confidence:** High (that it's benign).
- **Fix:** None required. The actor + identifier-keyed dedupe make this safe.

## Strengths
- **Correct off-main file I/O.** All disk reads/writes live on the `FileStore` *actor* (`Core/Storage/FileStore.swift:20`), so they run off the main thread automatically — no `DispatchQueue.global` juggling, and the main thread never blocks on YAML encode/decode or `FileManager`. This is the single biggest thing done right.
- **Atomic writes prevent half-read corruption.** `writeItem`/`writeList` use `write(to:atomically:true)` (FileStore.swift:62, 82), and because `FileStore` is an actor, `loadAll` (130) can never run *concurrently* with a write. A load-during-save reads either the complete old file or the complete new one — never a torn frontmatter. The "load reads a half-written model" hazard in my brief does **not** exist here.
- **Clean main-actor discipline for UI state.** `ItemStore` is `@MainActor @Observable` (Core/Stores/ItemStore.swift:6-8); every `lists`/`items` mutation is therefore on the main actor, and the SwiftUI views bind to it safely. The UIKit coordinators' delegate callbacks fire on the main thread, and every store call from them is either `await`ed from a `Task { @MainActor in … }` (e.g. ListDetailCollectionView.swift:1267, 1307, 1359) or routed through the synchronous `*Sync` helpers — no off-main mutation of `@Published`/observable state was found.
- **Sendable hygiene is correct.** `Item` (Core/Models/Item.swift:12) and `ItemList` (Core/Models/ItemList.swift:10) are value types conforming to `Sendable`, and `FileStore.LoadedList` is explicitly `Sendable` (FileStore.swift:116) — so the model crossing the actor boundary (FileStore → MainActor store) is checked-safe. No `@unchecked Sendable`, no `@preconcurrency`, and the only `nonisolated` usages are on pure model `Codable`/computed members, none of which touch mutable shared state.
- **No background mutation of the text storage.** `MarkdownStyler`'s direct `backing` mutation (the "bypasses the edit-notification path" comment in EditorCoordinator.swift:119-141) is a *UIKit edit-cycle* concern, all on the main thread inside `processEditing`/`replaceCharacters` — it is **not** a cross-thread race. The editor binding write-back (`textBinding.wrappedValue = …`) and save are likewise all main-thread, and the body is persisted only on an explicit `save()`/dismiss (ItemDetailSheet.swift:1085-1091), not per keystroke — so there's no editor autosave/edit race to begin with.
