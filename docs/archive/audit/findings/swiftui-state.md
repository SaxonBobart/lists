# SwiftUI Correctness, State Management & UIKit Bridges Audit

## Verdict
**Minor issues, leaning Solid.** The state architecture is modern and consistent: one `@Observable` store (`ItemStore`) injected by value, owned once via `@State` at the app root, with views reading it directly — there is **zero** legacy `ObservableObject`/`@Published`/`@StateObject` misuse anywhere in ~77 files, no double-init of stores, and clean `[weak self]`/`weak` discipline in every UIKit coordinator and toolbar (no retain cycles found). The two big sheets (`QuickCaptureSheet`, `ItemDetailSheet`) correctly snapshot their drafts into `@State` once in `init` and dirty-check against the original. The risky bits are concentrated where I expected them: the `ItemRow` cell hosts its **own** `.sheet` inside `UIHostingConfiguration` cells whose snapshots get reconfigured/reloaded out from under it (so the detail sheet can get dismissed mid-interaction), `SmartListCollectionView` reconfigures **every** visible cell on **every** store change (heavy + the same blank/teardown class the ListDetail code already works around), and the `applyXSync` fire-and-forget writes swallow disk errors. None are data-loss on the common path, but the first is a real, user-visible flakiness.

## Findings

### [P1] `ItemRow`'s per-cell `.sheet` lives inside `UIHostingConfiguration` cells that get reconfigured/reloaded — detail sheet can be torn down or fail to present
- **Where:** `Features/Today/ItemRow.swift:56,67,151` (`@State private var isShowingDetail` + `.sheet(isPresented:)`), hosted by `Features/SmartList/SmartListCollectionView.swift:138-153` and `Features/ListDetail/ListDetailCollectionView.swift:306-327`. Snapshot churn at `SmartListCollectionView.swift:167` and `ListDetailCollectionView.swift:459-472`.
- **What:** In the collection-view screens (Today / Scheduled / Flagged / Urgent / All / list detail), tapping a row's body opens the item detail through `ItemRow`'s **own** `@State isShowingDetail` and its `.sheet` modifier — the sheet is owned by SwiftUI content hosted *inside a `UICollectionViewListCell`*. That cell's hosting configuration is rebuilt whenever the diffable snapshot reconfigures or reloads the row. `SmartListCollectionView.applySnapshot` calls `snapshot.reconfigureItems(snapshot.itemIdentifiers)` (every row) on every `updateUIView`, and `updateUIView` runs on any observed store mutation. So a background change — e.g. a linger timer firing 1.5 s after a completion, a habit tick elsewhere, a reminder mutation — reconfigures the tapped row's cell, recreates the `ItemRow` value, resets `isShowingDetail` to `false`, and dismisses the just-opened sheet (or interrupts the presentation animation). The `ListDetail` author already discovered the sibling of this bug: the comment at `ListDetailCollectionView.swift:448-462` explains a just-completed "linger" row must be `reloadItems`'d (full cell recreation) because reconfigure "blanks the hosted `ItemRow`." A full reload of a cell that is currently presenting a sheet is exactly the teardown case.
- **Impact:** Intermittent: a user taps a task in Today, the detail sheet appears, then ~1.5 s later (linger timer) or when any other item state changes, the sheet closes by itself or stutters. Hard to reproduce on demand, easy to hit in normal use. The swipe-action "Details" path (`onShowItemDetail` → parent `@State detailItem`) is **not** affected because that sheet is owned by the parent screen — which is exactly why the row-tap path should use the same mechanism.
- **Confidence:** Med-High. The reconfigure-resets-`@State` behavior of `UIHostingConfiguration` is well-established; I could not run the sim to film it, but the code paths line up and the in-file comment confirms the related blank/reload behavior.
- **Fix:** Route the row-body tap through the parent like the swipe action already does. Add an `onOpenDetail: (Item) -> Void` to `ItemRow`, have the body `Button` call it (instead of setting `isShowingDetail`) whenever the closure is provided, and have both collection views pass `onShowItemDetail`. Then delete `ItemRow`'s internal `.sheet`/`isShowingDetail` (or keep it only for the pure-SwiftUI `List` callers — see P2). One parent-owned `.sheet(item:)` is immune to cell recycling.

### [P2] `SmartListCollectionView` reconfigures every visible cell on every snapshot apply
- **Where:** `Features/SmartList/SmartListCollectionView.swift:160-169` (`applySnapshot` → `snapshot.reconfigureItems(snapshot.itemIdentifiers)`).
- **What:** Unlike `ListDetailCollectionView` (which reconfigures only an explicit `reconfigure:` set and reloads only linger rows), the smart-list bridge unconditionally reconfigures **all** rows on every `updateUIView`/`applySnapshot`. Each reconfigure rebuilds a SwiftUI `UIHostingConfiguration` (`ItemRow`) for every visible cell. `updateUIView` fires on any observed `store`/`prefs` change. So toggling one item, or a linger timer tick, re-hosts the entire visible list.
- **Impact:** Wasted work on every interaction (CPU/allocations, possible scroll hitches with long Today/All lists); and it is the mechanism that makes P1 fire broadly. Functionally the list looks fine, so this is "smell + perf," not a crash.
- **Confidence:** High (it's literally `reconfigureItems(allIDs)` every time).
- **Fix:** Diff-driven updates: let the diffable data source compute insert/delete/move from stable identifiers and only `reconfigureItems` the rows whose *content* actually changed (track a per-row content hash, or reconfigure just the ids present in both old and new snapshots whose backing `Item` differs). At minimum, skip the blanket reconfigure when the snapshot's item set is unchanged.

### [P2] `applyUpdateSync` / `applyReorderItemsSync` / `applyReorderSectionsSync`: fire-and-forget writes with swallowed errors and unordered persistence
- **Where:** `Core/Stores/ItemStore.swift:162-183` (`applyReorderItemsSync`), `200-212` (`applyUpdateSync`), `449-470` (`applyReorderSectionsSync`).
- **What:** These mutate the in-memory `items`/`lists` synchronously (correct, for the drag-preview-before-animation reason documented), then spawn `Task { try? await store.writeItem(copy) }` per change. `FileStore` is an `actor`, so individual writes don't corrupt each other — but (a) each `try?` **silently discards** any write error, so if a write fails the in-memory snapshot and disk diverge with no signal, and (b) separate `Task {}` blocks have no ordering guarantee relative to each other or to a subsequent `update(_:)`, so two rapid drags/edits to the same item could land on disk in the opposite order to the user's actions (last-write-wins by completion time, not by intent). On a single local device this is low-probability, but it's a durability/observability gap in the source-of-truth layer.
- **Impact:** Rare lost edit or stale-on-disk row after a failed/again-reordered write; nothing surfaces to the user. Mostly a latent risk that becomes real once sync (future) reads `modifiedAt`.
- **Confidence:** Med. The actor prevents corruption; the gap is error-swallowing + ordering, which I can reason about but didn't stress-test.
- **Fix:** Funnel the fire-and-forget writes through a single serial persistence task/queue (e.g. an `AsyncStream` of write requests drained in order) so writes apply in submission order; and capture write failures somewhere (a `@Observable` `lastWriteError` the UI can surface, even minimally) rather than `try?`. App-root `bootstrap()` already only `print`s its error (`App/ListsApp.swift:19`) — same theme.

### [P2] Three competing item-detail presentation paths on the same row
- **Where:** `Features/Today/ItemRow.swift:151` (internal sheet), the swipe "Details" action `onShowItemDetail` wired in `ListDetailView.swift:114` / `TodayView.swift:32` / `SmartListScreen.swift:47`, plus direct `ItemRow` use in `Features/Tags/TagsOverviewView.swift:61` and `Features/Search/SearchResultsView.swift:31` (which rely on the internal sheet).
- **What:** A row can open its detail via (1) its own `@State` sheet, (2) the parent's `detailItem` sheet from the swipe action, and in Tags/Search only (1) exists. The two mechanisms present *different* sheet instances and have different lifetimes. This is the root cause behind P1 and a maintainability hazard: the "correct" path differs by screen.
- **Impact:** Inconsistent behavior screen-to-screen; the internal-sheet path is the fragile one (P1).
- **Confidence:** High.
- **Fix:** Standardize on parent-owned `.sheet(item:)` everywhere (see P1). Tags/Search would each gain a `@State detailItem` and pass `onOpenDetail`. This collapses three paths into one.

### [P2] `SheetDismissInterceptor` reaches into `connectedScenes` and reassigns the presentation controller's delegate
- **Where:** `Design/Components/SheetDismissInterceptor.swift:50-88` (`didMoveToWindow` + `installIfNeeded` walking `connectedScenes`/key window, reassigning `presentationController?.delegate`).
- **What:** To intercept swipe-to-dismiss it walks `UIApplication.shared.connectedScenes` to the key window, finds the topmost presented VC, and **takes over** `presentationController.delegate`. It re-installs on `didMoveToWindow` and again on the next runloop because "SwiftUI sometimes re-asserts the delegate." This works on single-window iPhone but is inherently fragile: hijacking SwiftUI's presentation delegate can break SwiftUI's own dismissal/`onDismiss` plumbing, and the "topmost presented VC" assumption breaks with stacked sheets / popovers / multi-scene (iPad, Stage Manager). It's used by both 1000+ line sheets.
- **Impact:** Today: probably fine (iPhone, one sheet at a time). Future/edge: discard-guard could attach to the wrong VC when a sub-sheet (e.g. `SectionPickerSheet`, `RepeatCustomSheet`) is also up, or fight SwiftUI for the delegate. The very need to re-install "on the next runloop" signals the race is real, just usually won.
- **Confidence:** Med (works in the common case; the fragility is structural).
- **Fix:** Prefer SwiftUI-native `.interactiveDismissDisabled(isDirty)` + `.presentationConfirmationDialog`/manual confirm, if the desired Reminders-style "attempt → popover" can be reproduced with it on iOS 26; otherwise scope the VC lookup to *this* representable's own window/`presentationController` (walk up from the bridge view's own `window`, which it already has) instead of the global key window, and avoid the speculative re-install.

### [P3] `CVSectionHeaderRow` rename `@State` lives in a cell that gets reconfigured
- **Where:** `Features/ListDetail/ListDetailCollectionView.swift:1803-1879` (`CVSectionHeaderRow` with `@State isRenaming/renameText` + `@FocusState`), reconfigured via `applySnapshot(reconfigure: [.sectionHeader(key:)])` at lines 215, 263.
- **What:** The inline section-rename text field keeps its in-progress text in `@State` inside a hosted cell. Expanding/collapsing that same section (or a sibling) calls `applySnapshot(reconfigure:)`, which the code guards somewhat (reconfigure is filtered), but any reconfigure that hits this row mid-rename would reset `isRenaming`/`renameText`. Narrower than P1 (rename is a brief, focused interaction and the chevron toggle reconfigures only that key), so lower severity — but same structural pattern.
- **Impact:** Edge: a snapshot apply landing while the user is mid-rename could drop the half-typed name. Unlikely in practice.
- **Confidence:** Low-Med.
- **Fix:** Lift rename state to the parent (`ListDetailView` already has `renamingSectionId`/`renameBuffer` `@State` that appears unused for this path — `ListDetailView.swift:48-50`) and drive the field from there, or commit on every keystroke.

### [P3] `ListDetailView` carries dead SwiftUI-renderer state and helpers after the UIKit migration
- **Where:** `Features/ListDetail/ListDetailView.swift:48-50` (`renamingSectionId`, `renameBuffer`, `renameFocus`), `375-391` (`commitSectionRename`), `409-456` (`uncategorized`, `sections`, `items(in:)`, `sectionName(for:)`), and the `// Legacy SwiftUI rendering (removed)` comment block at 348-355.
- **What:** The list body is now rendered by `ListDetailCollectionView`; several `@State` fields and computed helpers from the old SwiftUI `List` renderer remain but appear unreferenced by the live view. Section display logic is now duplicated between `ListDetailView` (`sectionName`, `sections`) and `ListDetailCollectionView` (`sectionDisplayName`, snapshot builder).
- **Impact:** No runtime bug; maintainability — two sources of truth for sectioning invite drift, and dead `@State` is confusing.
- **Confidence:** Med (couldn't prove zero references via compiler, but read every body path).
- **Fix:** Delete the unused fields/helpers; keep section-key logic in one place.

### [P3] `--ui-testing-reset-data` deletes the entire Lists root before the store is constructed
- **Where:** `App/ListsApp.swift:25-31` (`listsRoot()` calls `FileManager.default.removeItem(at:)` when the launch arg is present).
- **What:** Guarded by a launch argument, so not user-reachable, but it's a `rm -rf` of the source-of-truth directory executed in a static helper during `@State` initialization. If that arg ever leaked into a non-test launch (or a future automation), it's silent total data loss. Flagging for awareness, not as a live bug.
- **Impact:** None in production; catastrophic if the flag is ever set in a real session.
- **Confidence:** High (it does exactly this).
- **Fix:** Also gate on a `#if DEBUG` compile guard so release builds physically cannot execute the wipe.

## Strengths
- **Uniformly modern state model.** Single `@Observable` `ItemStore` created once (`App/ListsApp.swift:5` via `@State`), passed by reference, read directly by views. No `@Published`/`ObservableObject`/`@StateObject`/`@ObservedObject`/`@EnvironmentObject` anywhere — so none of the classic double-init / lost-`@StateObject` / over-`@ObservedObject` bugs exist. `ListViewPreferences`/`AutoListPreferences` are `@Observable` reference types held in `@State` (stable identity) and exposed for two-way binding via `@Bindable` only where needed (`SettingsView`, `EditListsSheet`). Textbook for iOS 17+/26.
- **No retain cycles found.** Every UIKit coordinator closure and the `MarkdownReminderToolbar` use `[weak self]`/`weak var coordinator`; `EditorCoordinator` holds the text view weakly; layout config swipe providers capture `[weak coord]`. The `Coordinator.parent` strong reference is the correct UIViewRepresentable idiom (struct value reassigned each `updateUIView`).
- **Sheet draft ownership is correct.** `QuickCaptureSheet` and `ItemDetailContent` initialize all `@State` from the incoming item once in `init`, never read the live model in the body for editing, and dirty-check via `composedItem() != originalItem`. `ListDetailView` deliberately documents reading the *live* list through a computed accessor (`ListDetailView.swift:29-35`) instead of snapshotting at navigation — exactly right.
- **View identity is stable.** `ForEach`/snapshots key on real model ids (`item.id`, `list.id`, section UUID strings, `SmartListGroup.id`) — no `id: \.self` on volatile values, no index-as-id in the data lists. Diffable snapshots use stable `Hashable` enums.
- **Navigation is value-typed and clean.** Single `NavigationStack` with a `NavigationPath` and typed `navigationDestination(for:)` for `SmartList`/`ItemList`/`SystemDestination`; sub-list push uses `navigationDestination(item:)`. Sheets use `.sheet(item:)` with `Identifiable` payloads (`CaptureTarget`, `detailItem`, etc.).
- **The hardest file is genuinely careful.** `ListDetailCollectionView` (1880 lines of diffable + hierarchical drag/drop) avoids the obvious traps: it never early-returns mid-drag in a way that strands the snapshot, it explicitly chooses `reloadItems` vs `reconfigureItems` for the linger-blank case, it cancels drag/drop state on `dragSessionDidEnd`/`dropSessionDidEnd`, and the cycle/depth guards (`isDescendant`, `depthOf`, `subtreeDepthOf`) carry `visited` sets to survive a corrupted tree. The "apply sync before `coordinator.drop`" rationale is sound and documented.
