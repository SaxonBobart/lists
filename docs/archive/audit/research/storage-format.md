# Storage Format — Validate the "Markdown + YAML frontmatter as the database" bet — Research

## Bottom line (3–5 sentences, plain English, for a non-technical product owner)
Files-as-truth is the **right strategic call** for Lists' three core promises — privacy, longevity, and sync-later. It's the proven model behind every app users praise for "owning their data" (Obsidian, NotePlan, TaskNotes), and when Logseq tried to move *off* plain files into a database in 2024 it triggered a community backlash precisely because the files were the selling point. But "files-as-truth" and "load every file with one big `try`" are two different decisions, and Lists has only made the first one well. The audit's P0 — one corrupt file wedging the entire library on "Loading…" — is **not** an argument against files; it's the single most important thing to fix *because* you chose files. The clean fix is the industry-standard hybrid: keep pure files as the source of truth, add per-file isolation so a bad file is quarantined not fatal, and (later, for scale) build a **rebuildable SQLite index** as a throwaway cache, never as the truth.

## What the landscape / best practice looks like (May 2026)

**The "you own your files" movement is mainstream and durable.** Obsidian's entire pitch is "a knowledge base that runs on a local folder of plain-text Markdown files," and the reasons users cite are exactly Lists' promises: notes work offline, "will never be held hostage behind a paywall," and "can be opened with any text editor forever" ([eesel/Obsidian overview](https://www.eesel.ai/blog/obsidian-overview), [SitePoint](https://www.sitepoint.com/obsidian-beginner-guide/)). NotePlan stores "all your content in portable plaintext files" with the same `---`-delimited YAML frontmatter Lists uses ([NotePlan frontmatter](https://help.noteplan.co/article/237-frontmatter)). This is the gold standard for the privacy-first segment.

**The cautionary tale: Logseq tried to leave.** Around May 2024 Logseq announced a "database version" that would *not* use Markdown files (export-only), because Markdown/Org files were causing real engineering pain. The community pushback was sharp — users "disliked the prospect of their content being locked away in a database structure they don't have ready access to," and noted "the plain files were the main selling point" ([Logseq forum](https://discuss.logseq.com/t/database-version-too-drastic-choice/20346), [Zylstra](https://www.zylstra.org/blog/2024/05/logseq-goes-the-database-route/)). The lesson for Lists: the file format *is* the product moat for this audience; don't trade it away.

**The real, documented downsides of pure files — all of which Lists will hit:**
1. **No transactions / no atomicity across files.** "Plain-text Markdown files lack built-in transactional guarantees" ([Guidest](https://guidest.com/markdown/front-matter/) and the practical reports below). A multi-file change (move an item between lists, cascade-delete a sub-tree) can't commit or roll back as a unit — exactly the shape of audit bug `DI-2` (cross-list move writes the new file but the old one lingers → a "zombie" item).
2. **No skip-the-bad-file resilience by default.** Loading is only as robust as you write it. Apple's own ecosystem reports show a single malformed file derailing tools; this is the class of audit `DI-1`.
3. **Performance at thousands of files.** Obsidian users report vaults of ~40,000 notes becoming "almost completely unusable" on an iPhone 14 Pro, with link-autocomplete taking "4 seconds between each letter" ([Obsidian forum: 40k notes](https://forum.obsidian.md/t/performance-issues-on-iphone-14-pro-with-large-vault-40-000-notes-using-obsidian-sync/98759), [large vaults](https://forum.obsidian.md/t/slow-performance-with-large-vaults/16633)). The cost isn't the files — it's *re-scanning and re-parsing all of them* for every query. Lists' smart lists are live queries over all items in memory, so it inherits this ceiling.
4. **Sync conflicts.** Once files sync (the planned paid feature), naive folder sync produces conflict files: "every time you type… a sync-conflict file is created" is a common Obsidian-on-Dropbox/iCloud complaint; the standard advice is "avoid Git unless you're comfortable resolving merge conflicts manually" ([Syncthing forum](https://forum.syncthing.net/t/multiple-sync-conflicts-when-writing-text-files/17466), search corpus). Lists is ahead here — it already carries `deleted_at` tombstones and a `lamport` clock on lists for future reconciliation.
5. **Frontmatter schema drift.** A present-but-mangled value silently changes meaning (audit `DI-3`: a corrupt `deleted_at` decodes as "not deleted" and resurrects an item). YAML's flexibility is also its hazard.

**The alternative Lists could have used — SQLite/GRDB/SwiftData/Core Data — and the trade.**
- **What you gain:** real transactions/atomicity (a move or cascade-delete commits or rolls back as one unit), indexed queries (`SELECT … ORDER BY … LIMIT 10` instead of scanning every item), referential-integrity constraints, change-observation, and proper read/write concurrency. GRDB makes "the database file the single source of truth," runs concurrent reads via WAL/`DatabasePool`, and exposes immutable record values safe across threads — and explicitly contrasts this with Core Data's per-context "constant threat of conflict errors" ([GRDB WhyAdoptGRDB](https://github.com/groue/GRDB.swift/blob/master/Documentation/WhyAdoptGRDB.md)).
- **What you lose:** the store becomes **opaque** — "the underlying SQLite storage created by [Core Data/SwiftData] is opaque to direct manipulation" ([cocoacasts/SwiftData considerations corpus](https://distantjob.com/blog/core-data-vs-swiftdata/)). No "open it in any text editor forever," no `git diff`, no inspecting your data without the app. For Lists that is the *whole promise*, gone. (Also: SwiftData needs iOS 17+ and is a "data is an object" abstraction; GRDB is "data is a database" and needs hand-written SQL — both add a dependency the founder's lean, native-only philosophy would resist.)

**The pattern that resolves the dilemma — files-as-truth + a *rebuildable* SQLite index.** This is now an established, named pattern: "The domain files are always canonical — the database is a disposable cache you can rebuild from them at any time… If the schema changes, drop the database and re-index" ([metafunctor: SQLite-as-cache](https://metafunctor.com/post/2026-03-20-the-mcp-pattern/)). Concrete numbers: a 951-page site re-indexes fully in **~6 seconds**; backups stay trivial because "the database is derived from [the files]." The same pattern powers `memweave`, `sqlite-memory`, `MarkdownDB`, and `zk_index` ([memweave](https://towardsdatascience.com/memweave-zero-infra-ai-agent-memory-with-markdown-and-sqlite-no-vector-database-required/), [zk_index](https://github.com/pithuene/zk_index)). You get SQLite's query speed without surrendering portability, because the index is throwaway and the files remain the truth.

**Interop conventions — and an important mismatch.** There are two competing task-on-Markdown conventions:
- **Obsidian Tasks (the popular one)** keeps tasks as **inline checkbox lines with trailing emoji**: `- [ ] Pay phone bill 📅 2026-05-30 🔁 every week ⏫`, where 📅 = due, 🛫 = start, ⏳ = scheduled, 🔁 = recurrence, and `⏫/🔼/🔽` = priority ([Tasks Emoji Format](https://publish.obsidian.md/tasks/Reference/Task+Formats/Tasks+Emoji+Format)). Many tasks live in *one* note's body.
- **TaskNotes (the closest analog to Lists)** uses **one task per Markdown file with YAML frontmatter** — status, priority, due, contexts, recurrence, tags — and treats "frontmatter as the machine-readable layer and the note body as the human-readable layer." Crucially, **property keys are configurable** (map `due`→`deadline` etc.) and the data is "a standard format with broad tool support" ([TaskNotes docs](https://tasknotes.dev/), [TaskNotes core concepts](https://tasknotes.dev/core-concepts/), [taskforge](https://taskforge.md/blog/tasknotes-integration/)).

Lists' model (one item = one `.md` file, fields in YAML frontmatter) is **architecturally identical to TaskNotes**, not to Obsidian Tasks. But the key *names* differ: Lists uses `created_at`, `modified_at`, `completed_at`, `due`, `goal_per_cycle`, `list`, `parent` (snake_case, confirmed in `Item.swift:142-169`); TaskNotes/Obsidian frontmatter conventions lean toward `due`/`scheduled`/`tags`/`priority` and Obsidian's first-class `tags:` list. Lists already matches the most important ones (`due`, `priority`, `tags`).

## Implications for Lists ← the most important section

1. **Keep files-as-truth. It's correct, and it's the moat.** Do not be tempted toward Core Data/SwiftData/GRDB-as-truth. The Logseq backlash shows the audience punishes apps that hide data in an opaque store, and that audience is exactly who Lists' privacy/longevity pitch targets. The DI-1 P0 is an argument *for* hardening the file path, not for abandoning it.

2. **Fix the read path so one bad file is never fatal — this is the #1 priority.** Per the audit (`FileStore.swift:176` — `try itemFiles.map { try readItem(at:$0) }`), wrap each `readItem`/`readList` in `do/catch`, collect failures into a `quarantined: [(URL, Error)]` list, continue loading everything that parses, and **always set `isLoaded = true`** (in a `defer`/`catch`) so the app can never wedge on "Loading…". Move offending files to `Lists/.quarantine/` and show a non-blocking banner ("3 items couldn't be opened"). This is cheap and it directly neutralizes the highest-stakes failure in the whole app. (Pair with `DI-3`: make a present-but-invalid `deleted_at` *throw* into the same quarantine rather than silently un-deleting.)

3. **Adopt the rebuildable-SQLite-index pattern — but later, and only as a cache.** Don't do it now (in-memory `[UUID:Item]` indexing fixes the near-term O(n) smart-list/Today scans flagged in PERF-1/ED-2 far more cheaply). But design toward it: when the library reaches thousands of items, add a `Lists/.index.sqlite` that is *derived from* the files, can be deleted and rebuilt in seconds, owns no truth, and powers smart-list queries + search. This is the only move that gives Obsidian-beating query performance without giving up portability. Document the invariant in `AGENTS.md`: **files are canonical; the index is disposable.**

4. **Add explicit schema versioning to frontmatter now, while the format is young.** Add a top-level `v: 1` (or `schema:`) key to both `.md` frontmatter and `.list.yml`. Cost is one line; the payoff is that future format changes (and the planned sync) can branch on version instead of guessing, and round-trips through other editors are detectable. This is the cheapest insurance against the "frontmatter schema drift" downside.

5. **Make multi-file mutations transaction-like.** The lack of cross-file atomicity is the root of `DI-2` (cross-list move) and `DI-4` (out-of-order reorder writes). Give `FileStore` a `moveItem(_, fromListId:)` that does delete-old-then-write-new as one operation, and serialize per-item writes through a single queue so a drag's update+reorder land in order. You can't get true ACID from files, but you can make each logical operation a single ordered unit — which closes the observed corruption.

6. **On interop: you're already on the right convention (TaskNotes-style per-file YAML) — make two small, deliberate alignments, don't chase Obsidian Tasks.** (a) Keep one-item-per-file YAML; that's the portable, tool-friendly layer TaskNotes praises. (b) Where cheap, prefer the community-standard *key names* so a future export drops cleanly into Obsidian/TaskNotes: you already use `due`, `priority`, `tags` — consider documenting an export mapping (`created_at`→`created`, `completed_at`→`done`/`completion`, `parent`→a wikilink) rather than renaming internal keys. (c) **Do not** adopt the inline-emoji Obsidian Tasks format as your storage — it's a different architecture (many tasks per note) that fights Lists' one-file-per-item model. Reserve emoji/inline syntax, if ever, for an *export* target. (d) Lists' habit `completion_log` (a YAML date→count map) and `lamport`/tombstone fields are non-standard everywhere; that's fine for app-private fields, but they should live under clearly app-specific keys so other tools ignore them gracefully.

## Open questions / things to validate
- **At what item count does the in-memory model actually hurt on an iPhone?** Lists holds all items in memory and re-queries on every change; needs a synthetic 5k/20k-item profiling run to decide *when* the SQLite index becomes necessary (the audit's PERF findings suggest the in-memory scan bites well before file I/O does).
- **Will the planned "Lists Sync" sync the raw files, or sync at the model layer?** If it syncs files directly, expect Obsidian-style conflict files and design a merge/last-writer-wins policy around `lamport` + `modified_at` now. If it syncs the model, the files-as-truth invariant on each device still holds but the index/cache story changes.
- **Does any real export workflow exist yet?** The "you own your data" promise is only true if a user can actually get the files out (memory notes the iOS Export button + app-private storage). Worth confirming the export produces a vault another tool can open.
- **Frontmatter key stability:** are any consumers (the editor, search, future sync) hard-coding the snake_case keys such that renaming for interop later would be expensive? If so, lock the export-mapping approach in implication 6b rather than ever renaming.
