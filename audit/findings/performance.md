# Performance & Scaling Audit

## Verdict
**Minor issues, with two clear "feels slow" risks.** Disk I/O is genuinely well-designed — every edit touches exactly one file, never the whole library, and the full load runs once at launch. The data model lives entirely in memory as plain arrays, which is fine up to thousands of items. The two real hazards are both in the *rendering/styling* layer, not storage: (1) the markdown editor re-styles and re-lays-out the **entire** note body on every keystroke (quadratic typing on long notes), and (2) the smart-list collection view forcibly re-renders **every visible row** on every change. Neither bites a casual user, but both will become noticeable for a power user with long notes or large smart lists. Tree/query logic is mostly linear with a couple of nested-loop spots that are harmless at realistic sizes.

## Findings

### [P1] Markdown editor re-styles + re-lays-out the whole note on every keystroke
- **Where:** `Features/MarkdownEditor/MarkdownStyler.swift:97` (`processEditing`) and `:120-124`; `Features/MarkdownEditor/EditorCoordinator.swift:119-141` (`textViewDidChange`) and `:383-404` (`applyResult`)
- **What:** Each typed character runs `processEditing`, which re-applies base attributes and re-tokenizes the **entire** document (`applyLiveStyling(in: full)` over the whole string — line-by-line regex enumeration plus a document-wide fence scan), then explicitly forces `edited(...)` over the full range. Separately, `textViewDidChange` *and* every smart-edit `applyResult` call `invalidateGlyphs` + `invalidateLayout` over the **entire** character range on every change. So one keypress costs O(document length) for styling and O(document length) for glyph/layout regeneration. Typing N characters into one note is therefore O(N²).
- **Impact:** Short notes are instant. As a note grows long (rough estimate: noticeable lag around 5–10k characters / a few screens of text, clearly janky beyond ~20k), each keystroke visibly stutters, the caret lags behind typing, and scrolling-while-typing hitches. This is the single most likely place a real user first feels the app "get slow," because notes accumulate over time and the cost is quadratic.
- **Confidence:** High (cost is structural — confirmed unconditional full-range work on every edit; the code comments themselves acknowledge "re-attributes every line on every edit"). The exact character count where it's felt is an estimate; would confirm with a profiler on a long note.
- **Fix:** Restyle only the edited paragraph range (plus any open fence it participates in), not the whole document — `processEditing` already receives the edited range via `editedRange`/`editedMask`. Scope the `invalidateGlyphs`/`invalidateLayout` calls in `EditorCoordinator` to the changed paragraph(s) instead of `NSRange(0, length)`. The fence/cursor-context machinery can keep a cached token map and only recompute the touched lines. This turns per-keystroke cost from O(document) to O(line), and total typing from O(N²) to O(N).

### [P1] Smart-list & Today views reconfigure every row on every store change
- **Where:** `Features/SmartList/SmartListCollectionView.swift:160-169` (`applySnapshot` → `snapshot.reconfigureItems(snapshot.itemIdentifiers)`); driven by `updateUIView` at `:45-48`
- **What:** `applySnapshot` unconditionally calls `reconfigureItems` on **all** item identifiers in the snapshot, then applies. Because `updateUIView` runs on every `@Observable` `ItemStore` mutation (any toggle, edit, habit increment anywhere), the whole visible smart list re-runs every cell's `UIHostingConfiguration` builder each time. Each cell rebuild also does `parent.store.items.first(where: { $0.id == id })` — an O(items) linear scan (`store.items` is a plain array, `Core/Stores/ItemStore.swift:10`). So one toggle in a large smart list costs O(rows × items).
- **Impact:** Checking off a single item in a big Today/Scheduled/All view (hundreds of rows) re-renders every row and does a linear lookup per row. Estimate: smooth at tens of rows, perceptible jank when a smart list holds many hundreds of items (e.g. a heavy "All" view across thousands of items). Manifests as a beat of lag after each checkbox tap and during the linger fade.
- **Confidence:** High for the all-rows reconfigure (explicit in code). Medium on the exact felt threshold.
- **Fix:** Drop the blanket `reconfigureItems(snapshot.itemIdentifiers)` — diffable data source already animates structural changes, and content changes can be targeted (reconfigure only the rows whose item actually changed). Build an `[UUID: Item]` index on the store (or pass items into the snapshot as value-typed identifiers) so cell config is O(1) instead of a linear scan.

### [P2] List-detail snapshot rebuild is O(parents × items) on every change
- **Where:** `Features/ListDetail/ListDetailCollectionView.swift:68-72` (`updateUIView` → `applySnapshot(animated: true)`), `:369-441` (per-section filtering), `flattenWithChildren` at `:1688-1724`
- **What:** Every store mutation rebuilds the full snapshot. Building it filters `store.items` once per section, and `flattenWithChildren` then, for each top-level parent, runs `store.items.filter { $0.parentId == top.id }` (and again per child for grandchildren). That's a linear pass over all items for every parent → roughly O(parents × items) for one list's render. Cell registrations additionally do `store.items.first(where:)` per dequeued cell (`:296`, `:229`).
- **Impact:** A single list with a few hundred items and lots of nesting will rebuild relatively expensively on each edit. Most lists stay small so this rarely bites, but a power user's mega-list (500+ items, deeply threaded) will feel a lag on every toggle/reorder. Less severe than the two P1s because it's per-list, not per-library, and most lists are modest.
- **Confidence:** High on the algorithmic shape; Medium that users hit list sizes large enough to feel it.
- **Fix:** Precompute a `parentId → [Item]` children map once per snapshot build (single O(items) pass) and have `flattenWithChildren` read from it, turning O(parents × items) into O(items). Reuse the same `[UUID: Item]` index for cell lookups.

### [P2] Search runs a full linear body scan on every keystroke, no debounce
- **Where:** `Features/Search/SearchResultsView.swift:73-90`; invoked live from `Features/Sidebar/SidebarView.swift:66-68` (`isSearchActive && !searchText.isEmpty`)
- **What:** `results` filters all `store.items`, lowercasing and substring-matching `title`, the full `body`, and every tag, on every render. `SearchResultsView` is recreated as the user types (bound to `searchText`), so each keystroke is an O(items × average-body-length) scan with a fresh `lowercased()` allocation per item per keystroke. There is no debounce/throttle.
- **Impact:** Fine for hundreds of items. With thousands of items carrying long markdown bodies, each keystroke does meaningful work (lowercasing every body on every letter), so the search field can feel laggy while typing. Estimate: noticeable past a few thousand items with substantial notes.
- **Confidence:** High on the per-keystroke linear cost; Medium on the felt threshold.
- **Fix:** Debounce the query (e.g. 150–250 ms) before recomputing. Cache lowercased title/body or precompute a search index. At minimum, short-circuit body scanning when the title/tag already matched (already done) and avoid re-lowercasing unchanged items every keystroke.

### [P3] Sidebar count helpers each do an O(items) scan, multiplied by rows
- **Where:** `Features/Sidebar/SidebarView.swift:619-621` (`openItemCount`), `:606-612`/`:623-625` (`tileCount`/`tagsCount`); `Features/ListDetail/ListDetailCollectionView.swift:229` (sub-list open count)
- **What:** Each list row computes its badge count via `store.items.filter { $0.listId == ... }` — O(items) per row. Rendering the sidebar is therefore O(lists × items). Tile counts call `store.items(for:)` (a full filter+sort) once per visible tile. `flatTreeRows` (`:459-469`) also re-walks the tree on every body evaluation.
- **Impact:** Negligible for typical libraries (dozens of lists, hundreds of items). Only a contrived library (many hundreds of lists × thousands of items) would feel the sidebar redraw. Flagged for completeness.
- **Confidence:** High (cost is real); impact genuinely minor at realistic scale.
- **Fix:** Compute per-list open counts in one O(items) pass into a `[listId: Int]` dictionary and look up per row. Low priority.

### [P3] First-launch seed and tag rename/remove write items one file at a time
- **Where:** `Core/Stores/ItemStore.swift:30-38` (bootstrap seed loop), `:216-256` (`removeTag`/`renameTag` call `update` per item), `softDeleteList` cascade `:322-335`
- **What:** These loops `await store.writeItem(...)` once per item sequentially. Each write is a full YAML encode + atomic file write. For bulk operations (renaming a tag used on many items, deleting a large list subtree) this is N sequential disk writes on the actor.
- **Impact:** First launch seeds a small sample so it's fine. Renaming a tag applied to hundreds of items, or deleting a list with hundreds of items, will take a visible moment (sequential atomic writes). Not a hot path; users do these rarely.
- **Confidence:** High; impact low because frequency is low.
- **Fix:** Acceptable as-is. If it ever matters, batch writes or parallelize with a `TaskGroup`. Note this overlaps with the concurrency domain (fire-and-forget `Task` writes elsewhere) — here the concern is only count of writes, not ordering.

## Strengths
- **Incremental, single-file I/O is excellent.** `FileStore.writeItem`/`deleteItem` (`Core/Storage/FileStore.swift:77-96`) touch exactly the one `.md` file that changed — never the whole library. Edits are O(1) disk work regardless of library size. This is the right design for a local-first app and is the most important thing to get right.
- **`loadAll` is a single O(files) tree walk run once at bootstrap** (`FileStore.swift:130-195`, called from `ItemStore.bootstrap` `:24`). No repeated full reloads on trivial changes — the in-memory arrays are mutated in place after each write (e.g. `ItemStore.toggleDone:83-85`). No "reload everything after every edit" anti-pattern anywhere.
- **`pathById` map** caches list-id → folder URL so item writes resolve their directory in O(1) without re-walking the tree.
- **SmartList query predicates** (`Core/Queries/SmartList.swift:45-86`) are clean per-item boolean checks — a single O(items) filter pass, no per-item rescans of the whole collection. The expensive part is how often it's *called*, not the query itself.
- **Reorder writeback is minimal** — `reorderItems`/`applyReorderItemsSync` (`ItemStore.swift:139-183`) only write items whose `sortIndex` actually changed, not the whole list.
- **Habit heatmap is bounded and cheap** — `HabitHeatmap.buildCells` (`Features/Habits/HabitHeatmap.swift:69-85`) builds a fixed 53×7 = 371 cells with O(1) dictionary lookups; `HabitStats.streak` (`Core/Models/HabitCycle.swift:72-92`) is capped at 3650 iterations and only runs on the detail screen. No runaway date loops in a rendered list.
